# Reporch CLI 1.0 qualification gate

Reporch does not use a calendar waiting period as a substitute for release
evidence. A release candidate is eligible for 1.0 promotion only after the
exact published npm and GitHub artifacts pass every required qualification.

The release workflow must build, publish to the isolated candidate channel,
download again, and exercise all five supported targets. The gate includes:

- checksum, SBOM, npm provenance, and GitHub artifact attestation validation;
- fresh npm and standalone installation on macOS arm64/x64, Linux arm64/x64,
  and Windows x64;
- Device OAuth, DPoP credential restoration and rotation, device-session
  management, and remote revocation;
- all six problem types across all five package profiles;
- local runtime bootstrap and Studio validation against the production
  capability contract;
- source CI, fuzz, exact-image Studio qualification, and release digest checks;
- zero unresolved P0/P1 defects, critical security findings, authoring data
  loss, quota mis-settlement, or duplicate publication incidents.

RCs remain on npm `next` and GitHub prerelease. The exact stable candidate is
published to the isolated npm `candidate` tag and kept as a GitHub draft until
the same artifact set passes qualification again. Only the explicit promotion
command moves `latest` and publishes the stable GitHub release. A failed gate
leaves `latest=0.9.0`; a published bad version is never reused.

The scheduled RC regression monitor continues to test the version currently
pointed to by npm `next`. Its evidence is operational monitoring, not a minimum
number of elapsed days and not a release override.
